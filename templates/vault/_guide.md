# 写作规范

这个库是多个 AI 和人共用的长期记忆。目标是**任何一个 AI 新开会话时，读完目录就能接上之前的工作**。

## 1. 记什么

| 值得记 | 例子 |
|---|---|
| 用户的偏好、习惯、身份 | 回复用中文；代码注释用英文；界面偏好深色主题 |
| 用户的纠正和确认过的做法 | "这类问题直接重试，不用问" + 为什么 |
| 不看代码看不出来的项目知识 | 发布流程的坑、环境约束、某个设计为什么这样定 |
| 解决过的难题 | 现象 → 原因 → 解决办法 |
| 做过的决定 | 选了什么、放弃了什么、为什么 |
| 外部资源在哪 | 面板地址、工单系统、文档链接 |

## 2. 不记什么

- 看代码、看 git 记录就能知道的东西：代码结构、函数说明、提交历史。
- 只在当前会话有用的临时状态。
- **密码、token 不写进页面**：低风险的（本地开发、测试账号、内网设备）存凭据库（`memwiki_secret_set`），页面里写 `secret:<名字>`；银行、邮箱、主账号、生产环境的密码不要存。
- 没有核实过的猜测。拿不准的写进页面时标注"待确认"。

## 3. 怎么组织

- **一个主题一页，一个事实只放一个地方。** 别处需要时用 `[[双链]]` 指过去，不要复制。
- **写之前先搜索。** 有相关页面就更新它；确实没有才新建。
- 放哪个目录：`user/` 用户本人，`rules/` 给 AI 的规则，`projects/<项目目录名>/` 项目知识，`topics/` 跨项目知识，`howto/` 操作手册，`decisions/` 决策，`reference/` 外部资源。拿不准就用 `memwiki_remember` 记进 inbox，之后再整理。
- 页间引用使用 `[[双链]]`；相对 Markdown 页面链接会被 lint 报 `markdown_link`，先用 `fix: true` 按当前页目录转换，再做 move/merge。代码、图片和外部 URL 不转换，无法安全转换的项需手改。
- 页面名用中文短语，能一眼看出内容，比如 `projects/myapp/发布流程`，不要用 `notes-1`。

## 4. 怎么写

- `summary` 必填：一句话、能单独看懂。它会出现在每个 AI 的开场目录里，是最重要的一行。
- 规则类页面（`type: rule`）写成三段：**规则本身**、**为什么**（用户的原话或背后的原因）、**怎么用**（什么情况下适用）。知道原因，才能在边界情况下做对判断。
- 日期一律写绝对日期（`2026-10-14`），不写"昨天""下周"。
- 写清依据：来自哪次会话、哪个文件、哪个链接，记到 `sources` 里；去重后只保留最新 10 条，新的在后。
- 正文简洁，用标题分节。正文硬上限 20 KB（UTF-8 字节），超过就拆成子页；已超限页面可继续删减正文，`meta/` 页面不限。
- `reason` 一句话说清为什么改；日志 reason 和 git 提交说明超过 120 字时保留前 120 字并加“…”；细节放正文或 `source`。

## 5. 怎么更新

- **纠正优先于补充，页面只写当前正确的说法。** 发现旧说法不对，直接改旧页面，不另建一页与错误说法并存。历史依据留在 git，不在正文堆“以前……后来……”。
- 改一节用 `memwiki_write mode=section`（正文不重复写标题）；改一句用 `edit` 的 `old/new`；`old` 必须恰好出现一次。补充独立内容才用 `append`（正文用 `text`），整页重写用 `replace`（可同时用 `meta` 更新摘要）。
- `create` / `replace` / `section` 必须显式传字符串 `body`，缺了报 `INVALID_META`；需要清空时传空字符串。所有工具拒绝未知参数，不能把 `body` 写成 `content`。
- 页头 `status` 只有 `active` / `stale`；MCP `meta` 传对象，`tags` / `aliases` 传字符串数组。
- 先 `memwiki_read` 拿 rev；除 create/append 外写入都带 rev。遇到 `CONFLICT` 重新读取，在最新内容上再改，不能强行覆盖。每次写入写明 `reason`，有依据就写 `source`。
- 新建返回 `SIMILAR_EXISTS` 时先读候选，优先更新它；确认是不同主题才用 `force: true`，`reason` 说明为何独立，理由原样留日志。不要为绕过拦截换标题或反复新建。
- 两页重复或整页过时被另一页取代时用 `memwiki_merge`：先读各页，确认独有内容已在归属页；用 `body` 传整理好的正文、目标页 rev。源文件直接删除，双链自动改到归属页，源标题和别名并入目标 aliases。原文可查 git 历史。不会自动替你判断什么事实正确。
- 发现两处说法矛盾：以当前核实、有依据的为准，直接改掉旧说法，在 reason 说明依据，不能仅凭日期新就认定正确。
- **写入时已核实就用 `memwiki_write` 的 `verify` 字符串参数写明依据**：同次写入刷新本地核实日期，stale 恢复 active，只记一条日志和一个提交。`memwiki_verify`（可传 note）用于只核实不改内容的旧页，无需 rev；刚写完的页面不要再调 verify。涉及代码、配置、路径的旧记录先核实再用；不能确认就保留 `status: stale` 并标“待核实”。

## 6. 工具

优先用 `memwiki_*` 工具，它们会处理版本冲突、链接、目录、日志和 git 提交。

生成的 `index.md` 与月度日志 `log/YYYY-MM.md` 不手改；日志只向当月文件末尾追加，`memwiki_log` 从最新月份往前读取，够条数就停。

没有工具可用、只能直接改文件时：保持页头格式不变，更新 `updated`、`updated_by`，然后用带写入方前缀的信息提交，比如 `git commit -m "[codex] 更新 topics/xxx：原因"`。

- **禁止改写 git 历史**：不要 amend 或 rebase 已推送的提交，不要 force push，不要压缩（squash）历史，不要删除或重建 `.git`。服务器已禁止强制推送。memwiki 工具用不了时，只能直接改文件后做一次普通提交。

## 7. 任务开始与回忆

1. 调用 `memwiki_context`（会话开始已注入就跳过），看相关目录。任务开始若本会话没读过本规范，`memwiki_read _guide`。
2. 有可能相关就 `memwiki_search`，用两三个中英文关键词。用户说“之前”“上次”时先搜，不凭印象说没记过。
3. `memwiki_read` 读全文，核实涉及当前环境的内容。判断是否值得写入：换一个 AI、下周新开会话，没有它会不会做错事或多走弯路？会才记；拿不准归属先用 `memwiki_remember` 进 inbox。

## 8. 凭据取用

不要先向用户索要，依次完成：
1. 搜服务名找 `secret:<名字>` 引用或“去哪里拿”的位置说明。
2. `memwiki_secret_list` 核对名字与 scope；页内清单可能过时，以凭据库为准。
3. `memwiki_secret_get` 写清具体 purpose，只按 scope 使用；不回显给用户，不写进任何文件、页面、提交或日志，用完不保留。
4. 凭据库没有、页面也没写去哪拿，才问用户。用户明确要求记住低风险凭据时用 `memwiki_secret_set`，带 scope，页面只留引用。高风险凭据遵循第 2 节禁存规则。

## 9. 整理与反馈

- 用户要求整理记忆时用 `memwiki-curate`：跑 lint，核对 overlap / fact_repeat 的事实归属，以 merge/edit 收敛到一页，其余链接过去；修改时用 verify 参数顺带核实，只核实旧页才单独 verify；不能核实就标待核实；inbox 已归入正式页的条目才移除。删除前确认信息已在归属页存在。
- overlap 是正文重叠警告；fact_repeat 是低级别提示，同一 IP、版本、路径或端口出现多页不一定有错，链接引用是正常的。不要机械批量删改。`fix: true` 只用于可安全自动修复的项，内容重复与反馈不能自动修。
- 遇到工具 bug、反复失败/难用、缺失能力、规则不清，或多次换关键词仍搜不到本应存在的知识时，用 `memwiki_feedback` 写 kind、title、scenario、expected、actual，留下可复现场景；先 `action=list` 看有没有同一问题，避免重复反馈。
- 一次普通零结果搜索、新主题本来没记过、按提示重读即可解决的一次正常冲突、瞬时网络问题，不必记反馈。不要把会话流水、用户私密原文或凭据塞进反馈；问题描述只保留定位所需内容。
- 反馈在 `meta/feedback/YYYY-MM`，默认状态 open；确认已有修复或规则澄清后 `action=resolve`，给 id、resolution（如“v0.2.0 修复”）。不能用“已反馈”当“已解决”。
- 整理时用 `memwiki_feedback action=list` 和 `memwiki_usage` 汇总未处理反馈与使用信号，**只汇报不改代码**。规则措辞可直接改库内 `_guide` 并留日志；工具行为或代码改进需另行确认方案再实施。不要重装 skill 来改规范。
- 使用信号仅为改进工具：本地 `.memwiki/usage.jsonl` 不进 git，超过 1 MB 轮转保留一份；只记录零结果搜索、版本冲突、密钥拦截、编辑找不到/不唯一、相似拦截和成功强制新建，查询疑似凭据时脱敏；不统计正常搜索、阅读或其他成功写入，空计数会提示“这段时间没有发生这些事件”，不记录正文、写入理由或凭据值。
